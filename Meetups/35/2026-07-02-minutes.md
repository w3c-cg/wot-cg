### Meetup Presentation

Ege: We welcome Sherif from Microsoft. He is a principal software engineer at Microsoft and is responsible for developing a multi-agent physical AI platform spanning edge runtime, messaging, and AI lifecycle surfaces.

Sherif: I am going to present my personal side project. This is not a Microsoft product, and the presentation does not represent Microsoft's position.

Sherif: My project is called Thingctx, and I am going to show how a TD enters the agent loop. Agents need self-describing things. In the past, readers were browsers and gateways. The pattern of describing systems is not new; we have a couple of examples from the past, such as XDR, WSDL, and OpenAPI.

Sherif: The new readers of these languages are agents. Even if TDs were not designed for a specific model, agents can still read them and operate with them.

Sherif: Currently, when using agents, we build integrations by hand, writing MCP tools and skills.

Sherif: There is no agreed way of describing what a system does and how to reach it. A TD covers the usual aspects of interacting with a system, such as typing, security, transport, and events. We have the contract in the TD for an agent to use the system.

Sherif: TDs and tools look very similar.

_shows TD action and tool spec side by side_

Sherif: They look the same, and security can be handled by a side secure channel. There is no code running here; they are just described by TD. This resolution is also deterministic. The same TD produces the same code.

Sherif: We can have deterministic mapping and tool code. The open question is naming. In TDs, names are unique within a TD. However, an agent would only understand a long list of tools. Therefore, some affordances would collide with the same tool name.

Sherif: I used node-wot and Eclipse Ditto and was able to interact with things created by both libraries. The only contract between them was the TD.

Sherif: The mapping works. You connect Thingctx inside your agent loop. No server or bridge is needed. The mapping alone is sufficient.

Sherif: Thingctx can also act as an MCP server to control multiple TDs. TDs can be invoked by CLI, and a skill can also drive the CLI. No server at all. Thingctx is still a runtime.

Sherif: Events also survive this integration with MCP.

Sherif: There are three layers, and only one needs a standard:
- mapping: TD -> tool
- tc: extensions via JSON-LD, targeted at LLM use cases
- consumer-side: event buffering and MCP limits

Sherif: A TD is a stable representation of a system. The mapping can change, and people would still get the benefits of a TD.

Sherif: You can install it with pip install thingctx. I also wrote a mapping document, and you can help to fix it if you find any issues. Can a model write a TD? We can already do that today, but the hard part is trust. An autogenerated description is safe if you check it against the real system.

## Q&A

Cris: You showed a mapping between TDs and tools, but it is more a mapping between affordances and tools. You lose the contextual information of the wrapper around the affordances (for example, this collection of tools is for a pump). How do you cope with this loss of information?

Sherif: Well, you could send the TD in the context, and what you would get is better tool-calling accuracy. But then you run easily into increased token usage in exchange for accuracy. Sometimes that is okay.

Cris: Another way could be having a TM and a way of searching the right TD and affordance (another tool?). Then you can generate the right call on the fly in the runtime.

Ege: How did you come up with this?

Sherif: I knew WoT since my PhD times. I started this project to solve an issue I had with implementing many MCP servers. I even tried to design my own description language. However, WoT is quite solid, and I used it.

Ege: We have space available in the next charter where we can introduce more specifications on how to write TDs, such as best practices for LLMs.

Ege: And what about semantics?

Sherif: Yes, that is an open problem too and quite interesting to work on.

Ege: In our case, deployers have specific software (management software) that adds the right information.

Sherif: You can use LLMs to infer semantics; that is an interesting area. But there are always trust issues.

Sherif: I am also looking into media streaming.

Ege: Do you need additional parameters rather than content type for media streaming?

Sherif: Yes, quite a few. Integrating with MCP is also challenging.

Ben: Very interesting talk. We recently discussed in the Community Group using WoT as an interface for agents to interact with the physical world. What do you think is better: tool calling or MCP proxying?

Sherif: Using TDs with LLMs involves a trade-off between token budget and accuracy. Small TDs are of course better. Many TDs are also problematic.

Ben: Can it be a multi-stage process, like discovery and selecting the right Thing Description?

Sherif: Chicken-and-egg problem. You can search only with a query.

Cris: Searching can be expressed as much as the query language allows.

Ben: Yes, there might be some interesting things in the description and its title. Describing a generic API with WoT is a little weird to me.

Sherif: Yes, but if you can make a better description that is more extensible than MCP and works better, why not?

Ege: Not putting everything in the MCP could be security by obscurity? There should be a mechanism to avoid using anything in a TD.

Sherif: I added an extension to allow human-in-the-loop feedback.

Cris: Sometimes actions cannot be performed because complex conditions need to be evaluated.

Cris: To see a future where it becomes a product?

Sherif: Only if there is a community around it.
